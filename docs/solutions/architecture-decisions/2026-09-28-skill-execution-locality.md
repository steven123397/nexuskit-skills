# 以 nk-work 为范式：执行规则就近读取，共享规则单源维护

## Context & Problem Statement

原来的 nk-work 要求执行者从 SKILL.md 跳到 implementation-loop.md，再转向 testing.md 和多个共享约定。有些规则已在本地写过，却仍要求跳转核对。文件按维护主题拆分，导致一次实际动作所需的规则散落在不同位置。

2026-09-28，用户确认重构后的 nk-work 可作为后续技能整理的范式。采纳的是内容组织和执行边界；这不表示其他技能已经迁移，也不表示真实客户端运行效果已经验证。这里保留设计理由，执行时仍读取技能本身，不要求 Agent 额外加载本记录。

## Decision Drivers

- 执行者应能按主流程完成当前任务，不必沿多层链接拼装规则。
- 共享规则仍需单一维护源，允许受控的短片段副本，避免人工改写后各自漂移。
- 减少读取和维护负担时，保留真实调用链、测试、集成、外部状态和验收等具体质量要求。
- 保持工具箱、整套安装和多客户端中立；不为本次整理引入构建流水线或代理调度层。

## Considered Options

| 方案 | 收益 | 代价与本次取舍 |
| :-- | :-- | :-- |
| 所有共享规则在运行时沿链接读取 | 维护副本少 | 执行者承担拼装成本，且容易形成递归读取；不再作为唯一组织方式 |
| 将全部规则塞入 SKILL.md | 一次读取即可获得全部材料 | 无关分支也被加载，主流程难以辨认；不采用 |
| 构建时展开 include，发布生成目录 | 可自动组合规则 | 增加生成与发布链路；当前试点不引入 |
| 主流程 + 完整执行材料 + 条件分支，短底线受控复制 | 常用路径连贯，分支按需读取，共享源可核对 | 需要维护片段一致性和消费端字段子集；本次采用 |

## Decision Outcome

### 1. 按使用时机组织内容

| 内容 | 放置方式 | nk-work 的实例 |
| :-- | :-- | :-- |
| 流程顺序、分支入口和结束条件 | SKILL.md 直接表达 | 定位现场 → 接收输入 → 实施 → 新发现分流 → 审查与提交 → 汇报结束 |
| 每次都要遵守的短底线 | SKILL.md 内保留受控片段 | 真实验证、已定决策、升级确认、子代理提交边界 |
| 某条主路径的完整方法 | 一个可连续阅读的 reference | tdd-loop.md 合并实施与测试，不再拆成相互跳转的文件 |
| 仅特定场景需要的细节 | 由 SKILL.md 明确给出加载条件 | UI、非代码、仓库外状态、子代理 |
| 输入定位与消费端所需字段 | 本地 reference 保留所需子集 | intake.md 说明如何定位单元及读取验收字段 |
| 理由、来源、备选方案与验证历史 | 维护者文档 | 本记录、RFC、skill-sources.md |

不要机械要求所有规则都在入口，或每个 reference 都很短。拆分的判断标准是：执行者是否在同一阶段连续需要这些内容。正常代码路径仍需先读取 intake.md，再读取 tdd-loop.md；改善目标是减少递归拼装，不是声称每次只读一个文件。

### 2. 区分执行依赖、公共接口与资料链接

nk-work 的六个本地 reference 是叶子材料，由入口加载，读完返回主流程；不再要求它们跳向另一个规则文件才能完成当前动作。后续技能整理优先采用这种结构，但不据此禁止所有 Markdown 链接，也不将整仓共享角色方法立即复制进每个技能。

跨技能协作通过公开入口表达。nk-work 委托 nk-commit 维护 current 并提交，完成后直接结束；nk-handoff 仅在用户显式调用时保存未完成现场；不再读取其他技能的私有 reference。消费者只保留所需产物字段和更新要求，完整格式由生产方或共享约定持有；格式变更时核对消费端，避免子集漂移。

这次采纳不包含“发布包中禁止出现 ../”或“支持单技能独立安装”。正式支持的仍是整套安装，conventions 及共享角色方法仍随套件分发。

### 3. 共享底线在维护时同步

work-guardrails.md 保存四个底线片段的原文，SKILL.md 中的 fragment 标记块保存副本。维护时修改源与副本，再运行 tests/run_checks.py 检查一致性；执行时直接使用入口内的片段。

当前仅有一致性检查，没有同步生成脚本，也没有 build/dist 展开流程。不要将“检查副本一致”写成“已实现自动生成”。只复制短而稳定的底线，不把长约定整体粘入入口。

### 4. 执行边界明确，质量要求可操作

- 一次 nk-work 调用处理一个已确认的实施单元。完成或遇到无法自行解除的阻断后汇报并结束，不自动调用 handoff；不根据模型估计的上下文余量自动顺延。
- 客户端支持、当前指令允许时，由 Agent 决定是否委派；用户与项目限制优先。不要求用户先点名，也不强制派发。
- 子代理返回、主会话验收、Git 提交分别判断。主会话逐项核对结果，整合后亲自验证；提交边界是完整的已验证变化，不是代理人数或结束次数。
- 吸收 Ponytail 的“用更少自维护代码满足同一需求”：先理解真实代码与调用方，寻找既有实现和原生能力，再新增必要实现。不以删行数为目标，不减少需求、安全约束或验证强度。
- 精简时保留具体动作与证据要求。原来的压缩曾遗漏部分 CE 质量要求，后续已补回文本；不能据此宣称与 CE 的整条交付流程等价。
- 2026-09-28 联合重构后，nk-work 在提交前调用 nk-review；review 内嵌 simplify 分析并统一产出报告，修复与范围外阻断由 work 处理。debug 同样消费审查报告并直接修复查证成立的问题。具体调用规则以各技能公开入口为准，不额外串联独立 simplify。

### 5. 文案直接指导动作

开头先说明何时使用、接着做什么；一段只承担清楚的职责。避免“本文件规范当……时的……方式”等长定语，条件、动作和例外过多时拆句或分段。

例如：“修改用户界面（UI）、前端组件或页面布局时，按以下要点走查。”可读性本身是执行质量的一部分，不能仅靠减少字节衡量。

## Consequences

后续技能逐个审查时，沿用这套判断方法，不照搬 nk-work 的目录和文件数量。迁移前列出当前动作、条件、输入输出和质量要求，重组后逐项核对，尤其检查精简是否把具体动作压成空泛口号。

采用短片段副本后，维护者需要同步源与消费端；读取路径更浅，也意味着完整执行材料可能更长。这是为连续执行接受的取舍，不追求表面上的文件最少或完全无重复。

验证分两层：

- **已取得的机械证据**：本轮 nk-work 修改后，五项仓库检查、11 项测试及 git diff --check 通过。片段检查覆盖四段底线的一致性；这些检查不证明所有架构规则已自动化检查。
- **仍待取得的行为证据**：用户另行安排外部会话验证正常代码、非代码、UI、外部状态和委派路径。实际读取量、遗漏率与任务完成效果尚无对照证据，不把静态结构改善写成实跑收益。

当前分发决定继续有效；本记录仅调整其“所有技能都应直接引用共享约定”的内容组织假设。详见 [分发布局决定](2026-09-26-distribution-layout.md)。具体实现与上游取舍见 [技能来源记录](../../skill-sources.md#nk-work)，体系摘要见 [RFC](../../ideation/nexuskit-framework-ideation.md)。
