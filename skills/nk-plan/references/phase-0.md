# 输入承接、定界与档位

本文件完成输入判定，返回目标产物、采用的需求来源、输出路线、深度和阻塞。实际加载、范围综述和后续调度由入口负责。

## 核心原则（贯穿全程）

1. **Product Contract 是事实来源**：本次明确采用 [nk-brainstorm](../../nk-brainstorm/SKILL.md) 的需求阶段 Plan 为续作目标时，就地补全同一文件，不重新发明产品行为，也不另起第二个文件。
2. **写决策，不写代码**：记录做法、边界、文件、依赖、风险和测试场景。不预写实现代码、不写 shell 命令编排。高层设计可以用伪代码或 DSL 草图传达方向，效力由入口加载的设计材料统一定义。
3. **先调研再成形**：定稿前先看代码库、`docs/solutions/` 和必要的外部资料。
4. **按规模定篇幅**：小工作写紧凑的 plan，大工作写更多结构，方法论不变。
5. **规划期问题与执行期发现分开**：能在规划时回答的现在回答；取决于写代码后才知道的，明确推迟到实现时。
6. **plan 可移植**：它应能作为活文档、评审材料或 Issue 正文使用，不嵌入某个执行工具专用的指令。
7. **执行方向轻量携带**：请求、上游文档或代码现状明显要求测试先行、先做特征测试、以冒烟验证为主等非默认方向时，在相关单元里用一句自然语言写明，不做成枚举，也不写成逐步编排。
8. **尊重用户点名的资源**：用户指名的 CLI、文件、链接、先前产物是权威输入。不认识就先去发现（`command -v`、读取、抓取）；确实不可用就明说，不悄悄换成别的。

**质量底线**：清楚的问题背景与范围边界；需求可追溯到请求或上游文档；仓库相对路径；功能性单元写明测试文件路径；决策带理由；指出要遵循的现有写法；每个功能性单元列出具体测试场景；依赖与顺序清楚。关于现有代码和夹具的实质性说法要对照仓库核实；妨碍实施的前置条件未满足时记为阻断项。计划中新建的东西不需要已存在。

---


## 0.1 续写与路线判定

先读用户指定的资源；命名的文件、URL、CLI 或 MCP 是输入，不能未经查找就假定不可用。不可用时说明缺口。

- 明确续作需求阶段 Plan：绑定该文件，后续就地补全。
- 明确续写已有实施 Plan：保留有效决定与 U-ID，只补请求涉及的内容；依据缺口决定需要哪些调研和检查，不重跑全部流程。
- 明确重新深化完整且带 frontmatter 的软件 Plan：把文档作为目标，返回入口的交互深化路线。无 frontmatter 的非软件计划按非软件路线处理。
- 明确“先规划做法”：返回做法层路线；软件实施细节留到用户要求展开时再规划。
- 非软件任务：按交付物判断，Rust 学习大纲也是非软件；返回非软件路线。

## 0.2 找到相关材料，不等于认领旧任务

按以下顺序定位：用户给出的路径或明确接受的当前交接；docs/current.md 的下一步及相关 docs/plans 文件；其他历史需求材料。显式路径也可能仅供参考，须按用户说明确定用途。相关性优先看目标、范围和 topic，时间只作线索。

区分三种情况：

1. **明确续作**：采用原产物，在其范围内继续；规划深度按待补内容判断。
2. **只有相关材料**：复用事实、决定与来源，不因此把一个小请求升级为持久规划或覆盖旧文件。
3. **没有相关材料**：从当前请求建立必要上下文。

有多个候选且会影响本次产物归属时才让用户选；可仅作参考时不制造选择。对照最新明确意图，旧文档中已被否定的范围不再承接。当前纠正只影响局部时保留其他决定；涉及新取舍才询问。

采用上游后才执行以下保留方法。各路线都遵守入口的已定决策底线，需要完整标注规则时由入口加载。

## 0.3 以 Product Contract 为主要输入

本次已明确承接需求阶段 Plan 时：

1. 读 frontmatter、Goal Capsule、Product Contract、Open Questions、Sources（按标题定位，不读长附录）。
2. 告诉用户本次会在同一文件中补上实施规划。
3. **保留 Product Contract 的含义和稳定 ID（R/A/F/AE）**，除非规划发现直接冲突或用户已明确修订；未解决的冲突写成问题，不能用假设悄悄覆盖已定产品范围。
   * 保留的是决策，不是字节。不改变含义的重组是允许的：拆分过载的需求（原 ID 保留原核心意图，拆出部分取下一个未用编号）、把规则的完整表述移到管辖它的 R 上、删除没有链接的重复表述。拆分或移动后，所有 `Governs R…`、`Covers R…`、行内 `per R…` 引用都要改指向新的 ID。重组不能削弱限定条件、丢掉边界情况、或把产品约束降格成实现偏好——那是范围变化。
   * 补全后的 plan 里写一行 **Product Contract 保留说明**："Product Contract 未改动"，或"重组、范围不变：<旧 ID → 新 ID>"，或"已改动：<R-ID> —— <原因>"。**实质性的产品范围变化**要先和用户确认，再写实施单元。
4. 延续所有适用的 Product Contract 章节，作为规划与调研的主要输入。
5. 不另建重复的 plan。保留上游写入的 `topic:` 字段和 `<!-- nk-section: ... -->` 语义标记（如 `<!-- nk-section: work-relationships -->`）：它们供下游技能识别，就地补全时原样保留、不改写、不删除。

本次采用历史需求文档作为上游时：通读；说明它作为本次规划的上游；延续问题背景、参与者/流程/验收示例（保留 ID，作为单元必须遵守的约束）、需求与成功标准、范围边界、关键决策及理由、依赖与假设、未决问题（保留"阻塞/推迟"区分）；在 frontmatter 写 `origin:`，在 plan 中引用重要决策时注明 `(see origin: <路径>)`；定稿前逐节核对没有遗漏。

Durable 且没有采用上游时，从请求出发写出完整 Plan，`product_contract_source: nk-plan`。

承接 wayfinder Map 时，读取交接摘要及必要的 ticket resolution：目标、范围、已定决定及理由、排除方案、成功标准、证据与剩余未知。Map 是探索来源，不是需求阶段 Plan；不强制返回 brainstorm。明确要求标准实施 Plan 时走 Durable，由本入口整理 Product Contract，使用 `product_contract_source: nk-plan`，在 Sources 保留 Map/ticket 链接。已定决定直接承接，只补缺口；真正的产品阻塞按 0.5 处理。已有对应 Plan 则续写，不重复创建。交付时把 Plan 路径与提交等可追溯位置返回 wayfinder。

**已定决策与上游产品决策同等保护**：调研只能补充，不重问、不悄悄改写。发现矛盾证据时按严重程度处理：没发现问题 → 照常；可行但不理想 → 按已定执行，并在对应条目上附冲突说明；导致不可行、做错东西或有破坏性 → 停下，作为阻断项报告给用户。当前用户已经明确纠正的目标优先于冲突的旧条目；修改时保留其他有效内容与稳定 ID，不把普通澄清当成全盘作废。

## 0.4 没有需求文档或输入不清时的规划引导

* 先判断请求是否已足够清楚：问题背景、范围边界、成功信号已知或可记为假设 → 直接进入 0.5。
* 模糊点主要在产品层面（用户行为、范围定义）→ 建议 [nk-brainstorm](../../nk-brainstorm/SKILL.md)，同时提供在这里继续的选项。
* 用户表示不熟悉这个问题领域 → 建议 [nk-brainstorm](../../nk-brainstorm/SKILL.md)，尊重用户选择；在这里继续时，阶段 2 的提问改用"教学式"：先解释选项和后果，再让用户做真实选择。
* 继续在这里时，简短建立：问题背景、预期行为、范围边界与明显的非目标、成功标准、阻塞问题或假设。

**退出条件**（或用户明确要求继续）：问题背景已**明确陈述**；重要的范围内外边界已知；成功标准已知或记为假设。边界和成功信号可以用假设满足，问题背景不能——它是必填章节，假设出来的背景会把未经验证的猜测变成产品范围。请求只给了做法没给目标时，从请求自身的动机推出目标（做法成为 Goal Capsule 的 Means，而不是 Objective），推不出就问。

引导中发现重大的产品问题 → 再次建议 [nk-brainstorm](../../nk-brainstorm/SKILL.md)；用户仍要继续就要求写明假设。

**缺陷型请求**（"修一下 X 的 bug"、报错、回归）：代码可达时，提供改用调试流程的选项（NexusKit 的 [nk-debug](../../nk-debug/SKILL.md)；目标环境未安装该技能时用可用的调试方式），与继续规划并列。代码在另一个本地路径时，先说明要读哪个仓库、plan 写到哪里（默认写到目标仓库的 `docs/plans/`），再继续。无人值守时不提供这个选项，按用户的显式调用继续规划。

## 0.5 规划前先处理未决问题

上游文档中有"规划前需解决"之类的阻塞问题时逐条审视：确属技术、架构或调研问题的，转为规划期工作；会改变产品行为、范围或成功标准的，保留为阻塞。

仍有真正的产品阻塞时，说明清楚，并让用户选：回到 [nk-brainstorm](../../nk-brainstorm/SKILL.md) 解决，或把它们转为明确的假设或决定后继续。阻塞未解决前不继续规划。

## 0.6 选择输出档位与规划深度

基于请求点名内容的有限阅读（不派子代理）选择**输出档位**：

* **Direct**：一次就能说清、做完、验证，没有需要用户权衡的决策。
* **Chat brief**：范围有限，至多一个需要用户权衡的决策，没有风险面。
* **Durable**：其余情况。

将选定档位返回入口，由入口加载聊天输出方法；不在这里继续读取其他分支。拿不准时取更重的一档；阅读中发现需要用户权衡的决策、风险面或需要多轮验证，立即升档。以下情况一律 Durable：无人值守运行；请求明确要一个 plan、plan 文件或某种格式；请求是续做已有 plan 的某一项；涉及风险面（认证、支付、迁移、对外契约）。

Durable 再分**规划深度**：

* **Lightweight**：小、边界清楚、模糊性低。
* **Standard**：常规功能或有边界的重构，有一些技术决策需要记录。
* **Deep**：跨领域、战略性、高风险或高度模糊的实施工作。

深度不清时问一个针对性问题再继续。宿主有任务跟踪能力时，用它展示路线级进展；没有就照常进行，不在聊天里模拟。


## 返回入口

说明采用哪份材料、是否绑定原文件、尚有哪些阻塞，以及输出档位与深度。独立 Durable 在调研前确认范围，承接上游在写前确认规划覆盖；续写与深化只处理新增取舍，具体确认条件由入口持有。
