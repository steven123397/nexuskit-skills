# 产品方案比较

## 探索方案

仍有多个合理方向时，依据调研和对话提出 **2~3 个具体方案**；否则直接给出推荐方向。

至少包含一个非显而易见的角度——反转（反过来做会怎样？）、去除约束（如果 X 不是限制会怎样？）、或借鉴其他领域的做法。最先想到的几个方案通常只是同一条轴上的变体。每个方案都要过"反泛化"检验：如果它会出现在这类问题的通用清单文章里，就对照依据档案把它磨得更具体，或者删掉。

**先呈现方案，再评价。** 让用户先看到全部选项，再听推荐——先给推荐会过早锚定讨论。

需要视觉辅助或一次性原型时，返回入口按相应条件处理，再继续比较；本材料不另设表达方式确认。

合适时加入一个有意提高上限的备选：找出哪个相邻的补充或重新表述最能提升用处、累积价值或持久性，同时不带来不成比例的维护成本。把它作为挑战选项与基准并列，而不是默认项。工作已明显范围过大、或原样请求显然就是正确做法时省略。

Deep — product 层级中，备选之间应在**做什么**（产品形态、参与者集合、定位）上不同，而不是**怎么做**。实现层面的变体属于 feature 层级。

每个方案给出：
* 简述（2~3 句）
* 优点与缺点
* 主要风险或未知
* 最适合的情形

**方案粒度：机制与产品形态，不是架构。** 方案描述写机制层面的区别（"暂停作为规则属性" vs "暂停作为事件过滤器" vs "暂停作为独立实体"）和与产品相关的取舍（与套餐层级的耦合、复杂度、迁移难度）。不写实现细节——列名、表名、文件路径、服务类、JSON 结构、方法名，这些是 [nk-plan](../../nk-plan/SKILL.md) 的事。在头脑风暴阶段提前引入架构，会迫使用户基于有意保持浅层的调研做架构决定。

呈现全部方案后，给出推荐并说明理由。额外复杂度带来真实维护成本时偏向更简单的方案，但不要因为某个低成本、高价值的打磨不是严格必需就拒绝它。

一个方案明显最好、其他备选没有意义时，跳过菜单，直接给出推荐。

相关时，说明选择属于：沿用现有模式 / 扩展现有能力 / 全新构建。

用户选择方案时按入口提问底线使用单选（推荐项标注 `(Recommended)`）。选择过程中敲定的名称按入口的术语底线即时写入。


比较结束后返回入口，进入范围综述。
