# 产品需求的范围综述（2.5）

本阶段先按 [范围综述](../../conventions/scope-synthesis.md) 整理和呈现，使用“产品需求综述”预算。所有软件规模都运行；非软件路线跳过。综述只讨论产品范围，实现做法留给 nk-plan。无人值守按 [interaction-rules.md](interaction-rules.md) 处理。

## 本阶段如何进入下一步

用两个信号选路径：2.5 前是否问过阻塞式问题，以及 0.3 的规模。规模澄清、1.3 追问、展示过的方案选择算阻塞问题；内部分类、扫描、压力测试不算。

- **Path A**：未问阻塞式问题且为 Lightweight。只说“要做什么”，不列其他小节、不等确认。需要文件时同轮进入第 3 阶段，否则进入交接。
- **Path B**：问过阻塞式问题，或为 Standard / Deep。按共享方法展示范围综述并等待整体确认。没有待确认点也仍有这个检查点；内容充分的开场不能仅因没提问就误走 Path A。

Path B 可按“要做什么 → 关键取舍 → 不在范围内 → 延续 → 待确认点”组织，空栏目省略。结尾明确实际下一步：“确认后我把这些范围写入需求阶段 plan；也可以直接告诉我要改什么。”已决定不写文件时，改成已确定的去处；没有去处就说按要求不写文件。本阶段不承诺写提交说明。

待确认点应来自真实范围分歧或非显然后果，不用它补藏 1.3 本应解决的阻塞问题。修改、再次确认与同一决定反复修改按共享方法执行，继续选项的目标为“写入需求阶段 plan”。

用户改道时停止 brainstorm，按实际意图建议 nk-plan、nk-work 或 nk-debug，并提议在本会话加载。

## 确认后的文档结构

确认后，第 3 阶段写入需求阶段 plan。内部草稿不作为 `## Synthesis` 进入文档，只有"要做什么"一段作为 Summary 嵌入；其余内容融入 Product Contract 各节：

| 内部草稿 | 文档中的去处 |
| :-- | :-- |
| "要做什么" | Summary（1~3 行，面向未来） |
| 已陈述 | Requirements（带 R-ID，完整细节），需要叙述背景时也进入 Problem Frame |
| 推断 | Key Decisions（附理由）——用户在对话中接受的押注成为文档中的决定 |
| 范围外 | Scope Boundaries |
| 成功信号（已陈述或推断） | 行为验收条件写在对应 R；只有需求未承载的质量或交接信号写入 Success Criteria，其他位置引用而不重复 |

对话中的取舍小节融入 Key Decisions；"不在范围内"融入 Scope Boundaries。

已定决策按 [sections.md](sections.md) 写入 Key Decisions 并带 `session-settled:` 标注；行为规则仍完整写在对应 R，Key Decisions 只留来源、理由及所约束的 R-ID。不弱化为推断或假设；依据已确认上下文直接写文档时同样如此。

不写斜体的过程说明（"于 2.5 阶段形成……"）。Summary 与 Problem Frame 的分工见 [sections.md](sections.md)。
