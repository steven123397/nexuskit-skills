# 可视化探针

形状、布局、行为路径、状态或关系边界看图更容易判断时，用 Markdown 中的 mermaid 或结构化文字给最小草图，不启动网页服务、不实施界面。产品目标、证据和偏好等纯语义问题直接讨论。

## 选择表达方式

沿用用户本会话已有的草图或文字偏好；没有偏好时根据当前决定的表达需要自行选择。不要为每个决定先问一次“草图还是文字”。只有表达方式会显著改变成本或判断、且无法从现有偏好推断时才问。

若文字或静态草图不能回答真实手感、动效或真实数据表现，说明限制，回到入口的一次性原型条件；不能用草图假装已经验证交互。用户选文字后出现这种限制仍要说明，不把原偏好当作忽略限制的理由。一次决定有多条路径时先识别共同问题，不把同一产品决定拆成重复的媒介选择。

## 草图

画出能回答当前问题的最简单的东西，追求快速反馈而不是精致。

可以画：
* 粗略的行为草图（用编号步骤或 mermaid 时序/流程图）
* 低保真的布局分区（mermaid `flowchart` 表示区域组成与相对位置）
* 状态对比（并列的 A/B/C 描述或状态图）
* 流程图
* 简单的 A/B/C 对比

避免：品牌化元素、最终配色或字体、组件库级别的精确度、像素级布局、类似生产实现的细节、会被误读为确定界面承诺的细节。不画手绘的方框字符线框图——难以阅读，用 mermaid 或分区列表代替。

给草图标明"仅供确定方向"，并说明用户应该判断什么、应该忽略什么。

草图只在对话中出现，不写入 plan；需要保留时写到本次运行的临时目录。用户选中的方向作为决定写进 Product Contract；正式需求中的图由成文阶段核对，不能把临时草图直接当成已确认规格。

## 草图之后的反馈

给出草图后，对范围有限的反馈使用阻塞式提问（附自由文本兜底）：
* 按提问规则从 2~3 个方向中选择
* 某个方向还是混合
* 选定一个布局/状态/行为
* 接受某个选项并提出修改

好的提问：

> A、B、C 哪个方向最接近你想要的？想混合或调整也可以直接说。请判断行为形状，不必在意具体样式。

用户的回答是权威；草图只是辅助。
