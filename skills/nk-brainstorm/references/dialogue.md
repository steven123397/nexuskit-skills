# 需求探索：压力测试与对话

先复用现状证据；缺少影响产品判断的仓库事实时，由入口安排侦察。对话围绕用户、结果、范围和成功信号；已明确的答案直接承接。

## 产品压力测试

生成方案前，按本次规模检查实际缺口。它是内部分析，不是给用户的清单；具体且充分的请求可以没有新问题。已定决定不重复检验，未经检验的断言在这里核对一次。

### Lightweight

* 这是在解决真正的用户问题吗？
* 是否与已有功能重复？
* 有没有几乎零额外成本、却明显更好的表述方式？

### Standard：检查这些缺口

* **证据缺口**：开场断言有需要，但没指出目标用户已经为此做过的任何事——花过的时间、付过的钱、搭过的变通办法——让这种需要可以被观察到。存在时，问对方为此做过的最具体的事。
* **具体性缺口**：开场描述的受益者过于抽象，Agent 不悄悄编造"他们是谁、会有什么变化"就无法设计。存在时，请用户说出一个具体的人或一个窄的群体，以及功能上线后这个人有什么变化。
* **反事实缺口**：开场没有说明用户今天遇到这个问题时怎么办，也没说明什么都不做会怎样。存在时，问现在的变通办法是什么（哪怕很凌乱），以及它的代价。
* **执着缺口**：开场把某个具体方案形态当作要做的东西，而不是这个形态本应带来的价值，也没有与能带来同样价值的更小形态比较过。存在时，问能带来真实价值的最小版本是什么样。

以及两个综合问题——不是缺口视角，而是 Agent 在自己推理中权衡的产品判断：
* 附近有没有一种表述方式，能在不增加维护成本的情况下带来更多用户价值？如果有，它增加了什么复杂度？
* 结合项目现状、用户目标和约束，现在杠杆最高的一步是什么：按原样做、换个表述、加一个相邻功能、做简化，还是什么都不做？

优先考虑能让价值累积、降低未来维护成本、或让产品明显更有用的做法。用结论让对话更聚焦，而不是压过用户的本意。

### Deep：Standard 的全部内容，另加

* 这是局部修补，还是让整个系统朝它该去的方向前进？

### Deep — product：Deep 的全部内容，另加

* **持久性缺口**：开场的价值主张依赖于世界的某个现状，而这个现状在用户关心的时间范围内可能以可预见的方式变化。存在时，问这个想法在最可能的近期变化下表现如何——追问下去，不接受任何竞争者都能说的"水涨船高"式回答。
* 我们可能会不小心做成哪个相邻产品？为什么那是错的？
* 世界上什么必须成立，这件事才会失败？

这些问题迫使形成明确的产品主张，结果进入 Product Contract 的 Scope Boundaries（"Deferred for later"与"Outside this product's identity"）以及 Dependencies / Assumptions。

下节对话方法决定这些缺口如何作为追问提出：每个适用的缺口是一个单独的开放式追问（"存在时，问……"这一句就是追问内容），可以逐步提出，但都要在方案比较前问过。

## 协作对话

按入口的提问底线推进：用户先表达，再提出想法；选一个方向用单选，可并存的目标或约束才用多选。

**冲突检查——会改变产品决定时提出。** 用户使用的词与 `CONCEPTS.md` 冲突，或对系统行为的描述与已核实的代码或依据档案冲突时，先把冲突摆出来，再把用户的说法当作已定。用具体场景区分概念；冲突不影响决定时直接采用规范名称，不为纠词打断。

用户无法评估陌生领域的选择，或进入形状类决定时，返回入口加载对应条件材料；完成后继续当前讨论。

**对话要点：**
* 先问用户已经在想什么，再提自己的想法，避免被 AI 生成的框架带偏。
* 先宽（问题、用户、价值）后窄（约束、排除项、边界情况）。
* **严谨性追问在方案比较前完成，以开放式提出。** 压力测试发现的每个缺口单独作为一个开放式追问（一个追问对应一个缺口），可以按入口的批量提问规则把互不依赖的追问合并在一轮中（最多 3 个，各自编号）。追问可以和收窄问题穿插进行，但进入方案比较前，压力测试发现的每个缺口都要追问过。不要做成选项菜单：菜单会暗示哪些证据算数，让用户挑选而不是陈述事实。**存在"执着于某个方案"的缺口时，把它放在进入方案比较前的最后一个追问**，即使对话已经收窄出了形态也不跳过——它的作用是在方案比较继承用户的隐含框架之前检验它。追问的回答显示确实不确定时，把它作为明确的假设写进 Product Contract，而不是跳过。
* 澄清问题背景、验证假设、询问成功标准。
* 把需求写到足够具体，使规划不必自行发明行为。
* 只在依赖或前提实质影响范围时提出。
* 带着想法、备选和质疑参与，而不只是访谈。

**退出对话前：整合检查。** 在心里把用户说过的内容合在一起，提出对话还没触及的非显而易见后果。用户说的 X 加用户说的 Y 再加 Agent 默认的 Z，产生用户在逐轮对话中不太可能想到的下游影响时（"如果静音挂在规则上，又不在删除时提醒，那么删除规则会悄悄丢掉暂停状态"），现在就追问。每个真实的组合效应一个开放式追问。范围综述的待确认点只是兜底，不是现在能问却推后的问题清单。

**退出条件**（以下都满足，或用户明确要求继续）：主要参与者/用户已确定或标为未知；预期成果已说明；重要的范围内外边界已知；成功标准或验收信号已知或记为假设；压力测试发现的每个缺口都已追问或记为假设；没有待问的整合检查问题。已定决策对每一项都算已检验，不要重问。


## 术语在讨论中的处理

CONCEPTS.md 存在时使用其中规范名。遇到弃用同义词、两个概念混用、定义与已核实行为冲突时，只有影响本次决定才当场指出。含义过多时提出精确名称，用“一个用户属于两个团队时，这条规则归谁”等具体情景探清边界。

名称和含义敲定后按入口底线即时写入；仍可能改变的术语留在对话。已有条目能承载的含义只完善，不新开同义条目；曾混用的概念可在 Flagged Ambiguities 留一行。写后简短告知，成文时再对照最终用词，不把术语维护攒到交接。
