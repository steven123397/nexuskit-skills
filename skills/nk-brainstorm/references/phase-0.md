# 输入、续作与规模

按入口的路线顺序使用本文件，完成判定后返回入口，不在这里加载其他阶段。

## 续作与当前意图

有仓库时读取已有 docs/current.md。用户明确指定继续某主题或需求阶段 Plan 时，读取指定文件，承接有效决定和未决问题，更新原文件，不再询问“继续还是重来”。

仅自行发现相关的近期需求文件时，先看主题与本次请求是否同一件事；可用 topic 和内容定位，不能仅凭时间或同名认定。相关文档可以作为依据，只有是否续作会改变本次范围或产物、且意图不明时才问。用户明确要求重来则建立新产物，保留旧文件。

将当前明确目标与旧文档对照：用户已否定或修订的部分不再作为约束，记录新的意图及受影响部分；普通补充不作废其他有效决定。拿不准修改范围才问，不自动删除旧产物。没有仓库跳过文件续作检查。

## 分类与快速路径

按任务而非话题分类：构建、修改、设计软件走软件路径；在非软件领域探讨目标与选择走通用探索；简单求助、事实问题或单步任务直接回答。入口负责加载选中路线。

“本项目要不要采用 / 切换到 / 替换为某项技术”属于软件决策。核对适配度、迁移成本和价值，把维持现状列为正式备选，给出结论与理由；不采用可在聊天结束，采用后再界定要做什么。

已有验收、明确行为、现有模式及有限范围时，复用有效上下文，跳过不必要的扫描、压力测试和访谈；仍按下面的规模标准分类。局部缺口只补局部，之后返回入口的范围综述。开场完整与工作复杂是两件事。

## 判断规模

依据本次工作范围、风险、依赖和未定问题分级。先复用有效上下文，缺少会改变分级的信息时才做针对性读取；输入写得详细不构成升档理由：
* **Lightweight**：小、边界清楚、模糊度低；
* **Standard**：常规功能或有边界的重构，有一些决定要做；
* **Deep**：跨模块、战略性或高度模糊。

规模不清时问一个针对性问题再继续；仍不确定就取较重的一档。

**Lightweight 在对话中结束。** 结果是最终交付的一段话：要做什么、做了哪一两个决定、它们接下来去哪（[nk-plan](../../nk-plan/SKILL.md) 的输入或提交说明）。通常不写文件，不派侦察、不运行方案生成；需写文件时声明核实按入口第 3 步判断，具体仓库事实仍须有限读取核实。只有对话产生了下游需要以稳定 ID 记录的决定，或用户要求时，才写文件；此时成文阶段依据对话中的决定写入，Ready for Planning Check 只核对对话已确立的内容。

**单一工作单元检查。** 深入探索前，检查请求是否包含多个可以各自规划的产品成果：每个都有自己的用户价值或验收边界，可以不依赖其他部分单独交付。共享参与者、一个端到端成果、覆盖多个设备/服务商，本身都不构成拆分理由。发现多个时：
1. 用平实语言提出拆分，只写出现在能确定的关系：哪些依赖或促成其他部分、共享某条产品规则、可以独立推进；
2. 问用户本次头脑风暴负责哪一个（用户已选定则直接沿用）；
3. 只有选定部分产生需求、流程、验收示例以及后续的实施单元，其余部分只作为背景；
4. 保留对整体的当前理解，写入成文阶段的"How This Work Fits Together"一节，不确定的关系标为暂定；
5. 在 Goal Capsule 中点明当前部分，并说明其余部分不在本次范围内。

各成果无法单独产生价值或单独验证，或拆开会迫使本 Product Contract 编造缺失的共享行为时，保持为一个整体。本检查只收窄当前产物，不创建父 plan 或路线图。

**Deep 的两种子类型：**
* **Deep — feature**（默认）：已有产品形态作为决策依据，主要参与者、核心成果、定位和主要流程都已确立，本次在此形态内扩展或细化。
* **Deep — product**：本次要确立产品形态，主要参与者、核心成果、相对相邻产品的定位或主要端到端流程在实质上尚未确定。已有代码降低了这种可能，但不能排除——形态模糊的半成品工具仍属于这一类。它会在需求对话中触发额外问题，在 Product Contract 中增加额外章节。


## 条件信号与任务跟踪

标记视觉/空间决定及用户无法评估的陌生领域；入口在实际需要时加载条件方法，分类本身不先发一轮表达方式问题。

Standard/Deep 有宿主任务跟踪能力时列出查看依据、澄清范围、比较方案、确认范围、形成结果；按条件加入核实等工作。条件变化时标明跳过及原因，不把未做事项标成已验证；无此能力正常继续，不在聊天模拟清单。
