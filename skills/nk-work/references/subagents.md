# 子代理实施

客户端支持子代理、当前指令也允许使用时，Agent 可自行决定是否委派。无需等用户点名，也不要求每次都派发；用户的明确要求、禁令和项目限制优先。

决定是否委派时，考虑任务能否独立完成、隔离上下文是否有帮助，以及协调成本和文件冲突风险。适合委派的任务包括独立调查、阅读分析，或在干净上下文中完成一个明确的算法单元。

## 任务包

调用方提供目标、预期行为、允许修改的文件、禁止触碰的接口、已定决策、验证命令和返回内容。一个子代理只负责一个实施单元或一个明确子任务。

有相关经验时同时提供 solution 原始路径、适用条件、关键约束、验证影响及存疑状态，不只传临时摘要路径，不假定子代理继承会话记忆。告知已覆盖的检索范围，子代理只补自身任务的证据缺口。

任务包同时传入本次适用的质量要求：先查既有实现与原生能力，保留边界校验和真实验证；不要为了独立交付另造已有工具或引入无依据的通用层。只有依赖满足且修改范围互不冲突的任务才并行；有依赖或共享写入时串行推进。

## 回收

子代理返回的是待核对的结果，不是提交触发器，也不代表所属实施单元已经完成。子代理不执行 `git commit`。主会话逐项核对结论、证据和范围；有文件改动时检查 `git status` 与 `git diff`，确认没有范围越界。只读调查按证据核对，不产生代码提交要求。同一单元的反馈修正可继续交给原代理，验收后不要把下一单元追加给它。

相关子任务整合后，主会话必须在主环境亲自运行覆盖该交付变化的验证命令，验证最终实际文件状态，不能只拼接各代理的通过报告。无需因每个代理结束而重复运行整套检查；验证后的改动若影响已验证行为，提交前重新运行受影响的检查。

提交按完整、可独立验证的交付变化划分，不按代理人数或返回次数划分。多个代理共同完成同一变化时，实现、测试与配套文档合为一次提交；相互独立的变化可分别提交，但每个提交都须有对应验证。主会话确认交付边界与证据后，回到主流程调用 `/nk-commit`；不得为了回收代理而提交半成品。

结果直接返回改动文件、实际验证命令与结果、未验证项和阻断；重要反证不可省略。长调查材料只有在允许时才写入指定临时目录的独占文件，同时返回关键结论与绝对路径；写入失败则内联必要结果并说明缺口。

整合多个子任务时，核对它们是否重复新增同一种 helper、状态或依赖；只有行为与职责一致时才合并，刻意的隔离和差异继续保留。验收下一单元需要委派时使用新的上下文，不把上一代理的完整对话复制过去；不因结束派发而清理其尚未核对的改动。
