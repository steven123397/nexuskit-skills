根据当前对话和对代码库的理解，产出一份 spec。不要重新访谈用户，只整理已经知道的内容。

项目使用的 Linear 团队、项目和标签应已提供。如果缺少，先询问缺失的配置。

## 流程

1. 如果还没了解代码库，先探索仓库的当前状态。全文使用项目领域术语表中的用词，遵循相关 ADR。

2. 勾勒准备从哪些接口测试这项功能。优先复用已有测试接口，并尽可能从高层验证行为。如果需要新增测试接口，也放在尽可能高的位置。测试接口越集中越好，理想情况下只需要一个。

   和用户确认这些测试接口符合预期。已经确认过的直接沿用。

3. 按下面的模板写出 spec，再发布到项目的 Linear 中。使用项目已有的 spec 标签和状态；已有对应 spec 时更新它。

<spec-template>

## 问题

从使用者的角度说明遇到的问题，以及为什么值得解决。

## 方案

从使用者的角度概述准备提供的能力，以及它如何解决问题。

## 使用场景与预期行为

按有意义的场景组织自然语言叙述，讲清用户什么时候使用、为什么使用这个模块、如何使用，以及预期得到什么结果。必要时说明它在前后工作流中的位置。

覆盖范围内的重要行为与边界。角色差异影响行为时，说明不同角色的使用方式。

## 实现决定

列出已经确定的实现决定，可以包括：

- 要构建或修改的模块。
- 要修改的模块接口。
- 开发者给出的技术澄清。
- 架构决定。
- 数据结构变更。
- API 契约。
- 具体交互。

不要写具体文件路径或代码片段，它们很容易过期。

例外：如果原型中的片段比文字更准确地表达了一个决定（状态机、reducer、schema、类型结构），可以放在对应决定下面，并简要注明来自原型。只保留表达决定的部分，不放完整演示。

## 测试决定

列出已经确定的测试决定，包括：

- 如何通过外部行为验证，不绑定内部实现细节。
- 要测试哪些模块、接口和重要行为。
- 代码库中可借鉴的已有测试。

## 不在范围内

说明哪些内容不属于这份 spec，尤其是容易被误纳入的工作。

## 补充说明

仅在有其他必要内容时使用。

</spec-template>
