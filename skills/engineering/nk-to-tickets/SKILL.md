把 spec 或当前对话拆成一组 **tickets**：每张是一个纵向切片，用 Linear 原生阻塞关系声明它依赖的其他 tickets。

项目的 Linear 团队与项目应已提供，缺少时先询问。

## 流程

### 1. 收集上下文

从对话中已有的内容入手。用户传入引用（spec 或 map 的链接、编号）时，读取它的完整正文和评论。

### 2. 探索代码库（可选）

还没探索过代码库就先探索，了解代码的当前状态。ticket 的标题和描述使用项目领域术语表中的用词，遵循相关区域的 ADR。

寻找预重构的机会，让实施更容易：先让改动变容易，再做那个容易的改动。

### 3. 起草纵向切片

把工作拆成纵向切片 tickets：

- 每张切片窄而完整，穿过所有层（数据结构、接口、UI、测试）：纵向，不是只切一层的横向切片。
- 完成的切片可以独立演示或验证。
- 每张切片的大小以一个全新会话能完成为宜。
- 预重构先行。

为每张 ticket 标出依赖：必须先完成的其他 tickets。没有依赖的 ticket 可以立即开始。

**宽范围重构是纵向切片的例外。**宽范围重构是波及面横跨整个代码库的机械改动（改列名、改共享符号的类型）：单次编辑同时破坏大量调用点，任何纵向切片都无法独立保持 CI 绿色。不要硬塞进纵向切片，按**扩展–收缩**排序：先扩展，在旧形式旁边新增新形式，不破坏现状；再按波及面分批迁移调用点（按包、按目录），每批一张 ticket，被扩展阻塞，批与批之间 CI 保持绿色；最后收缩，没有调用方后删除旧形式，这张 ticket 被所有迁移批阻塞。当批次也无法独立保持绿色时，保持顺序不变，共用一条集成分支，共同阻塞一张最终整合验证 ticket；绿色只在最后承诺。

### 4. 与用户确认

把拆分方案列成编号清单，每张 ticket 展示：

- **标题**：简短的描述性名称。
- **依赖**：哪些 tickets 必须先完成；没有则注明可立即开始。
- **交付什么**：这张 ticket 让哪些端到端行为跑起来。

询问用户：

- 粒度是否合适？太粗还是太细？
- 依赖是否正确：每张 ticket 是否只依赖真正卡住它的 tickets？
- 有没有要合并或进一步拆分的 tickets？

迭代到用户认可这个拆分。

### 5. 发布到 Linear

按依赖顺序创建 tickets（被依赖的在前），再设置原生阻塞关系。来源是已有 issue 时，把每张 ticket 建成它的子 issue。使用项目已有的标签和状态，不在正文重复维护状态、优先级或依赖；无阻塞的 ticket 创建为 Todo，被阻塞的留在 Backlog，解锁后由实施会话推进。不关闭、不修改父 issue。

实施从**前沿**开始：所有依赖都已完成的 tickets。纯线性链条就是从上往下做。

每张 ticket 的正文：

<ticket-template>

## 所属 spec

<来源 spec 的链接；来源不是 spec 时省略本节。>

## 交付什么

<这张 ticket 完成的端到端行为，从使用者角度描述，不写成逐层实现清单。>

## 验收条件

- [ ] <可观察、可验证的完成条件>

</ticket-template>

避免写具体文件路径或代码片段，它们很容易过期。例外：原型中的片段比文字更准确地表达一个决定时（状态机、reducer、schema、类型结构），可以放进对应位置并简要注明来自原型。只保留表达决定的部分，不放完整演示。
