# 修复：测试证据、最小改动与回归

根因诊断完成且修复已获授权后使用。复用调查阶段的工作区基线和有效失败证据，不重复分诊；核对期间是否出现新改动。项目分支策略优先，不自动创建分支。

## 1. 确定修复范围与测试归属

明确本次修复涉及的行为、文件及与既有改动的重叠。已授权且归属清楚的在途工作可继续修改；归属不明或无法安全隔离的外来改动先厘清，不能覆盖。记录本次实际差异，提交时交回入口，不在本材料执行 Git 提交。

先查现有测试及适用的目录指导：

- 已有失败测试覆盖缺陷：直接复用，不另写同义测试。
- 现有测试过度 Mock 或未走真实触发链：针对性加强它。
- 现有断言与已确认的正确契约不符：修正断言并在改实现前确认失败；若它表达有意设计的行为，返回入口说明产品/设计分歧，不能为放行修复而改预期。
- 没有适当覆盖：在能触达真实缺陷的最小接缝补回归测试，名称说明症状与期望。
- 可用接缝无法还原缺陷：说明覆盖缺口，以原始复现或其他可靠观测验证，不写只能制造信心的浅测试。

测试通过真实入口检查结果、状态或边界副作用。预期来自独立的契约和已知结果，不由被测实现生成；内部因果链不 Mock，只在外部服务、时间等边界按需替代。真实入口可用时，不为测试增加专用生产导出或开关。

## 2. 先证实失败，再做最小修复

确认测试或复现因目标缺陷失败，而非搭建问题。已有证据对应同一待修状态时复用；状态已变或证据不足才补跑。

修复根因所在层，核对受影响的调用方和既有行为；同一因果修复可改多个配套文件，但不混入无关重构、格式化或顺手清理。不扩大需求，不削弱安全、兼容性与已有错误处理。

修复未让场景转好时，先判断是实现不完整、实验条件变化还是假设被证伪；说明具体证据，再回到调查。撤掉已否定的本次试验，保留用户原有改动，不让失败尝试累积。不能只因一次实现失败就声称整个理论已被推翻，也不能无新证据不断改同一理论的变体。

## 3. 验证原始场景与回归

运行回归测试并检查原始场景，不能只验证最小化后的用例。两者确为同一检查且内容未变时复用结果，不机械跑两遍。偶发故障报告同条件下的运行次数和失败率；性能问题比较同环境、同输入的指标。

按影响范围运行相关套件及适用的 build、typecheck、lint 和项目必需检查；无法划定影响范围时扩大验证。没有配置或环境不可用时写清未验证项，不把替代测试、Mock 或本地结果推断为真实外部环境已通过。

检查跨层副作用、共享调用方、错误传播，以及失败后的清理、重试或幂等性；只核对实际相关风险，不为凑类别增写测试。

## 4. 清理与交付证据

逐行自查本次 diff：是否还有临时埋点、一次性探针、已否定的修复、边界遗漏或无关改动。只清理本次产生的临时内容；需要保留的观测能力应作为明确的修复内容审查。尾部改动影响行为时补跑相关检查，清理后的最终状态才是交付对象。

汇总根因、修复范围、已有与新增测试、失败/通过证据及未验证边界，回到入口完成提交前审查与交付。分层防御或生产复盘按入口条件处理，不在此另开规则链。
