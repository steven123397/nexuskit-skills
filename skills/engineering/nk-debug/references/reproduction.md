# 构建与收紧复现回路

现有失败测试或操作已能可靠反映症状时直接使用。仅在缺少可用回路、运行成本妨碍调查或复现场景过大时使用本材料。

## 选择能到达真实故障的入口

优先利用现有测试和工具，按故障性质选择，不必依次尝试全部手段：

| 手段 | 适用情况 |
| :-- | :-- |
| 失败测试 | 已有单测、集成或端到端接缝可触达缺陷；修复后直接保留为回归测试 |
| HTTP / CLI 调用 | 服务或命令有明确输入与可断言的输出 |
| 浏览器操作 | 真实 UI、DOM、控制台或网络交互才会触发 |
| 捕获样本重放 | 真实请求、事件或日志中保留了关键状态；先脱敏并在隔离环境重放 |
| 最小运行脚手架 | 启动一个必要子系统即可触发；替代边界不能抹掉缺陷 |
| 属性或随机测试 | 输入空间大、边界未明；保留失败样本与随机种子 |
| 二分或差分回路 | 有已知正常/异常版本、配置或数据；同条件比较差异 |
| 人工在环 | 真实设备、登录或操作无法自动执行；给出具体步骤和需要回读的观测 |

记录命令或操作步骤、环境、输入和实际失败证据。断言精确症状，不以“附近也报了一个错”代替目标问题。人工反馈标明来源，不冒充 Agent 亲自执行。

## 收紧信号

- 缓存不变的准备工作，减少无关初始化，让反复执行成本可接受。
- 固定可控的时间、随机种子、网络与文件状态；不能为了确定性抹掉真实故障条件。
- 偶发故障在隔离环境中适度重复、加压或调整时序，报告尝试次数及失败率；运行预算按成本与证据价值决定，不无限循环或要求固定概率。
- 性能缺陷建立数值基线，记录数据规模与测量条件；“看起来更快”不是结果。

## 最小化到足以区分原因

保留原始场景用于最终验证。逐个或分组删减输入、调用、配置与准备步骤，每次确认仍是同一失败。结果相反时恢复相关因素，继续缩小范围；不能从一次偶发通过就断言删掉的部分是原因。

对载荷可删字段、缩短字符串和结构；对测试可减少准备与调用序列。目标是降低调查成本，不要求证明每个剩余元素都不可删除；继续削减不再帮助区分假设时停止。

## 仍无法复现

整理已尝试路径、已有观测与缺失条件，返回入口处理：获取故障环境、脱敏样本或人工观测；新增生产埋点等操作须有相应授权。没有复现不等于没有缺陷，也不等于修复已经验证。
