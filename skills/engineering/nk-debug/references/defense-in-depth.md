# 分层防御 (Defense-in-Depth)

当缺陷由"非法状态抵达脆弱代码路径"引起时，只修一层会让其他代码路径、重构或 Mock 有机会重新引入同一个缺陷。分层防御通过在多个层校验，让缺陷在结构上更难复发。

入口已根据实际复发路径或严重后果选择本材料。先确认需要防住的路径，再选择适用层；不按出现文件数量机械扩展。

## 四个层

按需选取，并非每个缺陷都需要全部四层：

| 层 | 目的 | 何时应用 | 示例 |
| :-- | :-- | :-- | :-- |
| 1. 入口校验 | 在 API 边界拒绝明显非法的输入 | 缺陷由调用方传入本应被拒绝的坏数据引起 | 任何下游代码触碰 `workingDirectory` 之前，先在其为空或不存在时抛错 |
| 2. 不变量 / 业务逻辑检查 | 强制数据对本操作而言是合理的 | 该操作有入口校验无法表达的前置条件 | 发起密码重置前断言 `user.state === 'verified'` |
| 3. 环境守卫 | 拒绝在讲不通的环境中执行危险操作 | 操作在错误环境中可能是灾难性的 | 测试环境（`NODE_ENV === 'test'`）下拒绝在系统临时目录之外执行 `git init` |
| 4. 诊断面包屑 | 在危险操作前留存取证上下文 | 其他层仍可能被绕过；未来的失败需要证据 | 执行 `git init` 前记录 `{ directory, cwd, env, stack }` |

## 应用步骤

1. 追踪坏数据从产生到症状之间流经的每个函数；
2. 标出检查点：其中哪些位置本可以更早拒绝这个坏值；
3. 在适当的层加守卫。每个守卫尽量窄——只校验本层负责的东西，不重复其他层的检查；
4. 独立测试每个守卫：构造绕过第 1 层的用例，验证第 2 层仍然接得住。

## 常见错误

- **每层重复同一个检查**：每层应捕获不同类别的失败。第 2 层只是复述第 1 层时，它就是噪音；
- **没有对应缺陷就投机地加守卫**：分层防御是对已观察到的失败模式的回应，不是通用的代码洁癖；
- **缺少必要诊断信息**：有现实绕过或复发路径时保留可定位的脱敏证据；不是每个修复都要新增日志。
