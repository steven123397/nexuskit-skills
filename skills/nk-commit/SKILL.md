# /nk-commit

所有本地 Git 提交统一经过本技能，包括用户直接调用和其他技能中的提交步骤。调用方提供交付范围、场景、验证证据及可选 U-ID；本技能判断时机并提交，然后返回。复用已有上下文；子代理不提交，主会话核对整合后的变化并执行。

## 1. 核对本次提交范围

读取项目提交约定，结合调用方信息与差异确定归属。不清楚时按需读 `docs/current.md`，只询问仍有歧义的范围，不接管无关脏文件。

- 运行 `git status --short --untracked-files=all`、`git diff` 和 `git diff --cached`，检查未暂存、已暂存及未跟踪内容；未跟踪文件另行读取。非 Git 仓库则停止，无本次可提交变化则报告并返回。
- 用 `git branch --show-current` 核对分支，遵守项目策略；无规定时留在当前分支，在默认分支提交时简要说明。detached HEAD 且目标分支不明确时先澄清，不擅自切换。
- 有 HEAD 时按需读取 `git log --oneline -10` 确认历史与风格；首次提交没有历史，按项目约定或第 4 步默认格式处理，不运行依赖 HEAD 的差异命令。

命令分别执行；PowerShell 中 revision 表达式如 `'@{u}'` 应加引号。保留外来修改与暂存内容。

## 2. 判断提交时机与边界

按用途而非扩展名判断。R1–R6 为唯一节奏规则；调用方提供场景和范围，不另写提交算法。

- **R1：交付变化。** 源码、测试、配置、技能、规则或文档本身构成已验证的交付成果时，正常提交；实现、测试与配套文档一起入库。Plan 单元进度以带 U-ID 和证据的提交为准，不为标记进度单独提交状态文件。
- **R2：中途状态记录。** 只有 current、Plan 进度或审查状态等过程记录时，暂留工作区，随下一次交付入库；符合 R3 或 R4 时按其处理。
- **R3：补记已有提交。** 仅补充当前会话最近交付对应的状态或沉淀材料，且目标就是 HEAD、确认未推送且未共享时，可 amend。已有共享历史不自动改写；证据不足时不 amend，按 R2 暂留或 R4 新建提交。
- **R4：规划、交接、收尾与知识维护。** 按下面四种场景处理，不把普通文档交付误归为过程记录：
  1. 会话交接：符合 R3 时优先并入最近交付，否则将交接材料合为一次提交，每个会话至多一次交接提交。
  2. 纯规划产出：同一会话继续实施时随首个交付提交；在规划后结束时，与 current、相关术语等一起作为交接提交，不另建规划提交。
  3. 分支收尾或发布日扫尾：调用方完成所需产物后，合为一次收尾或扫尾提交；本技能不接管清理、打 tag 或发布。
  4. 知识沉淀：优先随对应交付提交，已提交且符合 R3 时补记，否则留待下一交付或交接。知识审计有在途交付时默认搭载；没有可搭载工作或用户明确要求立即入库时，允许独立维护提交。
- **R5：状态文件更新边界。** current 仅在交接、外部阻断变化或版本／里程碑跃迁时更新，不是实时流水账。本技能不为提交主动改写 current；未验证项随验证汇报记录，需要交接时再由调用方登记。
- **R6：独立变化。** 可独立验证且文件范围能安全分开的变化分别提交；耦合变化一起提交，不限定提交数量。一组修复的审查记录随最后一个修复提交，不另建状态提交。

只有准备 amend 时才核实目标提交与发布状态：结合本会话操作记录及可用远端信息判断；`git log '@{u}..HEAD'` 只说明与该跟踪分支的差异，无 upstream 或过时的远端引用不能证明从未推送。无法确认就不自动 amend。

按文件划分范围，不使用交互式 `git add -p`。同一文件混有无关改动时，路径限定无法隔离它们；先厘清或安全分离，不能整文件带入，也不能为凑提交丢弃已有改动。

## 3. 核对审查与验证证据

接收调用方已完成的审查结论和实际验证命令、结果、未验证项，核对它们对应本次待提交内容。适用流程要求提交前审查但尚未完成时，返回缺口，不把测试通过视为已经审查；本技能不展开审查方法。

已有验证覆盖当前变化，且其后没有影响结论的内容变化时，直接复用，不因进入本技能再跑一遍。证据缺失、相关内容已变或项目明确要求时，仅补跑必要检查；需要实施或修复则返回对应流程。必需检查失败不提交；环境无法验证的部分如实标为未验证，并按交付条件判断是否阻断，不能虚报通过。

主会话须验证整合后的实际状态，不拼接子代理报告。提交范围核对不触发重复测试或审查。

## 4. 编写提交信息

风格优先级：用户明确要求、项目约定、近期提交风格，最后采用 Conventional Commits。语言沿用明确要求与项目惯例；均无约定时使用中文描述。采用该格式时：

```text
<type>(<scope>): <简短成果> (U-ID)

<必要的原因、方案与影响>

<1–3 行真实验证证据及未验证项>
<可选的不兼容说明与 Issue 关联>
```

- **类型**：`feat` 新功能、`fix` 修复、`refactor` 重构、`perf` 性能、`docs` 文档、`test` 测试、`style` 纯格式、`ci` 持续集成、`chore` 工具维护、`revert` 回退。按实际变化选择，不因本仓库交付物是 Markdown 就全部用 docs。
- **主题**：type 保留英文；scope 可省略，有则使用稳定的模块名。中文主题用动宾短语，简述成果，通常不超过 50 字符，不加句号，不写“更新代码”等空话。有 U-ID 才在末尾附带，不补造编号。
- **正文**：与主题空一行，说明必要的原因、方案或影响，不罗列文件。验证写实际命令、结果与边界；未运行不记为通过。长命令保持完整，不为换行改坏命令。
- **不兼容变更**：确实破坏已支持的接口、配置或数据兼容性时，用 `!` 或 `BREAKING CHANGE:` 标明，并说明迁移办法；不是所有 Schema 调整都算破坏性变更。
- **Issue**：一般关联用 `Refs #N`；只有满足该 Issue 的全部验收且符合项目关闭流程时才用 `Closes #N`，不把部分进展写成已解决。

例如：`fix(解析器): 修复空输入导致的崩溃 (U3)`。

## 5. 执行限定范围的提交

完整提交信息写入仓库外临时文件，避免 shell 转义。仅暂存本次明确的文件，包括已确认的删除；保留无关暂存内容。普通提交分别执行：

```bash
git add -- <本次路径...>
git commit -F <临时说明文件> -- <本次路径...>
```

符合 R3 时使用 `git commit --amend --no-edit -- <补记路径...>`；需更新说明则改用 `--amend -F <临时说明文件>`，仍限定路径。不用 `git add -A` 或 `git add .`，不使用未限定路径的 commit 吸收无关暂存内容。

提交失败时检查原因，不跳过项目 hooks。hooks 若改变了交付内容，重新核对差异并补充受影响的验证及必要审查，再重试；不把之前的证据直接套到变化后的内容。

## 6. 确认结果并返回

核对提交哈希、主题、文件范围，运行 `git status --short --untracked-files=all` 检查残留；amend 时区分原内容与补记。意外内容先报告，不自动改写共享历史。

返回已提交结果、暂留或阻断的内容与原因，然后回到调用方；直接调用则结束。不要求整个工作区变干净，不自动推送、创建 PR 或进入下一实施单元。
