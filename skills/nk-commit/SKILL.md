# /nk-commit

所有本地 Git 提交统一经过本技能。调用方提供范围、场景与证据；本技能维护 current、提交并返回。子代理不提交，由主会话核对整合后的变化并执行。

## 1. 核对本次提交范围

读取项目约定与 current，结合成果、范围、审查与验证证据、阻断、下一步和可选 U-ID 核对现场。直接调用复用上下文与差异，不另开调查或编造下一步；只询问归属不清的部分。

- 运行 `git status --short --untracked-files=all`、`git diff`、`git diff --cached`；另读范围内未跟踪文件。非 Git 仓库停止，无本次变化返回，不为了产生提交更新状态。
- 核对分支并遵守项目策略；无规定时留在当前分支，默认分支提交简要说明。detached HEAD 的目标不明确时先澄清。
- 有 HEAD 时按需读取近期 Git 记录确认归属与风格；首次提交不执行依赖 HEAD 的命令。

命令分别执行，`'@{u}'` 等参数正确引用。保留无关修改与暂存内容；同一文件混有无关变化时先安全分离或厘清范围，路径限定不能隔离文件内的改动，不使用交互式 `git add -p`。

## 2. 判断提交时机与边界

按用途而非扩展名判断。以下 R1–R6 为唯一规则正文，调用方不重复提交算法。

- **R1：完整交付。** 一个经过验证的变化一次提交，实现、测试、配套文档及相关 current 更新一起入库。文档、规划、规则也是交付物，不要求伴随产品代码；有 U-ID 时进度由对应提交与证据体现。
- **R2：中途记录。** 未完成的草稿、零散进度或审查状态默认暂留，随对应交付入库，不为刷新 current 单独提交。外部阻断可即时登记，但记录本身不自动触发提交；用户显式调用 handoff 或明确要求保存状态时按 R4 处理。
- **R3：遗漏补记。** 补记本会话最近交付的状态或沉淀，目标为 HEAD 且确认未推送、未共享时可 amend。正常交付应一次带齐 current，不先提交再固定补记；证据不足或已共享则按 R2 暂留或 R4 单独保存，不自动改写历史。
- **R4：不同交付场景。**
  1. 显式现场保存：用户明确调用 nk-handoff 或要求提交状态快照时，可提交准确记录的现场；未完成的产品改动仍留在工作区，不冒充完成。符合 R3 才补记，否则正常提交；无变化不提交。
  2. 规划产出：需求或实施计划达到本阶段交付标准后，通过本入口提交并更新 current，发想记录由用户决定是否提交。明确处于连续修改中的草稿暂留；后续没有新增变化则不重复提交。
  3. 分支收尾或发布日扫尾：所需产物与 current 合为一次收尾或扫尾提交；本技能不清理产物、打 tag 或发布。
  4. 知识维护：与当前交付相关的沉淀一起提交；交付后遗漏的材料按 R3 处理。可独立验证的沉淀或审计成果可正常提交，不必等待交接；未完成的部分按 R2 暂留。
- **R5：提交携带现状。** 每次提交前核对 current，有相关变化才更新；缺失时建立。记录成果、证据、阻断、残留和下一步，与本次变化同次入库；不因调用方结束或模型估计上下文不足自动调用 handoff。
- **R6：独立变化。** 能安全分开且可独立验证的变化分别提交，耦合变化一起提交，不限定数量。每次提交只记录该次交付已具备的能力；后续待提交内容记为残留，不能提前宣称完成。一组修复的审查状态随对应修复或最后一个相关提交入库。

准备 amend 时结合本会话操作记录与可用远端信息核实发布状态；`git log '@{u}..HEAD'` 只说明与该跟踪分支的差异，无 upstream 或过时引用不能证明未共享。不能确认就不自动 amend。

## 3. 核对证据并更新 current

确认审查与验证证据对应待提交内容。适用流程要求提交前审查但尚未完成时，返回缺口；不把测试通过视为审查通过，不在此展开审查方法。主会话须核对整合状态，不能只拼接子代理报告。

已有验证仍适用时直接复用。仅相关内容变化、证据缺失或项目要求时补跑必要检查；必需检查失败不提交，需要修复则返回实施流程。环境无法验证的部分标明未验证，按交付条件判断是否阻断。

读取 [current.md 格式契约](../conventions/current-md.md)（上下文完整且未变时复用），按本次交付更新必要字段，保留仍有效的阻断、决定及外来改动说明。调用方已更新的内容只核对，不重复改写。下一步仅写已有决定或有依据的建议，未知则注明未确定。

核对基点使用整理时已存在的提交；不把待生成哈希写入文件，不只为哈希变化制造差异。记录本次提交后预期仍残留的工作，成功后核对事实，失败则说明文件尚未入库。若 current 混有归属不清的编辑，先厘清，不覆盖或整文件夹带。

把有变化的 current 加入明确提交范围；缺少入口指引时在项目现有 AGENTS.md 或等价文件补最小指针，一起提交。检查记录与证据、路径是否一致；仅更新交接文字不重跑代码测试或重复审查。没有语义变化则保留原文件。

## 4. 编写提交信息

风格依次遵循用户要求、项目约定、近期惯例，默认中文 Conventional Commits：

```text
<type>(<scope>): <简短成果> (U-ID)

<必要的原因、方案与影响>

<1–3 行真实验证证据及未验证项>
<可选的不兼容说明与 Issue 关联>
```

- **类型**：`feat` 新功能、`fix` 修复、`refactor` 重构、`perf` 性能、`docs` 文档、`test` 测试、`style` 纯格式、`ci` 持续集成、`chore` 工具维护、`revert` 回退。按变化选类型，不因 Markdown 一律用 docs。
- **主题**：type 保留英文；scope 可省略，有则使用稳定的模块名。中文主题用动宾短语，通常不超过 50 字符，不加句号。有 U-ID 才在末尾附带，不补造编号。
- **正文**：与主题空一行，说明原因、方案或影响。验证写完整命令、结果与边界，未运行不记为通过。
- **不兼容变更**：实际不兼容时用 `!` 或 `BREAKING CHANGE:` 标明并说明迁移办法。
- **Issue**：关联用 `Refs #N`；满足全部验收及项目关闭流程才用 `Closes #N`。

## 5. 执行限定范围的提交

完整提交信息写入仓库外临时文件，避免 shell 转义。仅暂存本次明确的文件，包括已确认的删除；保留无关暂存内容。普通提交分别执行：

```bash
git add -- <本次路径...>
git commit -F <临时说明文件> -- <本次路径...>
```

符合 R3 时使用 `git commit --amend --no-edit -- <补记路径...>`；需更新说明则改用 `--amend -F <临时说明文件>`，仍限定路径。不用 `git add -A` 或 `git add .`，不使用未限定路径的 commit 吸收无关暂存内容。

提交失败时检查原因，不跳过项目 hooks。hooks 若改变了交付内容，重新核对差异并补充受影响的验证及必要审查，再重试；不把之前的证据直接套到变化后的内容。

## 6. 确认结果并返回

核对提交哈希、主题、文件范围，运行 `git status --short --untracked-files=all` 检查残留；amend 时区分原内容与补记。意外内容先报告，不自动改写共享历史。

返回已提交结果、暂留或阻断的内容与原因，然后回到调用方；直接调用则结束。不要求整个工作区变干净，不自动推送、创建 PR 或进入下一实施单元。
