# PR 描述规范

> 挂在 [nk-close](../SKILL.md) 第 6 步（PR 摘要）。蒸馏自 CE `pr-description-writing.md`：保留"写 diff 看不出来的东西"与"长度随决策成本伸缩"两条核心原则；裁掉 stack 叙事、概念教学归档与 branding（取舍理由见维护者文档 `docs/skill-sources.md` 的 nk-close 条目）。

## 核心原则：写 diff 看不出来的东西

diff 在 PR 页面已经可见。描述存在的意义是解释 diff 无法展示的：什么从不可能变成可能、什么从坏了变成修好、形态发生了什么变化。读者能从 diff 自己重建的句子，一句都别写。

- 差（罗列改了什么）："新增 `evidence-decider.ts`，修改 `SKILL.md` 调用它，更新两个测试文件。"
- 好（写出现在的不同）："证据捕获现在自动判断改动是否有可观察行为，CLI 工具与库和 Web UI 一样纳入范围。"

开头经不起"这是改了什么"还是"现在有什么不同"的检验，就重写。用户可感知的 bug 先写前后对比，技术原因只在有助于评估风险时提及。

## 长度随决策成本伸缩

**按决策成本定长度，不按 diff 行数。** 决策成本 = 评审者批准前还需要自己想明白多少东西；5 行的高风险改动可能比 500 行机械重命名需要更多笔墨。

| 改动画像 | 描述写法 |
| :-- | :-- |
| 小而简单（typo、配置、依赖升级） | 一两句话，不加小节标题 |
| 小而不平凡（bug 修复、行为变化） | 3~5 句；用户可感知的 bug 先写前后对比 |
| 中大型特性或重构 | 开头一两句自含一个完整想法；之后每个小节各回答一个评审者无法从 diff 得到的疑问；设计决策写明理由 |

中大型写法要点：**任意处可停**——只读开头的人也能说出这个 PR 改了什么、为什么是这个形态。验证证据写实际跑过的结果，不写"tests passed"这类空话；残余不确定性如实写出。蓄意推迟的范围用一句话声明。

## 标题

沿用项目提交信息风格（如 `type: description`）。没有用户明确确认时，不使用 `!` 或 `BREAKING CHANGE:`。

## 关联 Issue

- **真正完整解决**才写 `Fixes #N`（合并进默认分支时自动关闭）；多个 Issue 逐个重复关键词。
- 相关但不完全解决写 `Related: #N`，单独成句，不与 close/fix/resolve 类措辞混用。
- 不确定时按不关闭处理或省略，绝不发明关闭语义。

这与 [`../../conventions/issue-writing.md`](../../conventions/issue-writing.md) 第四节的关闭时机衔接：`Fixes #N` 是 Issue 三个合法关闭时机之一。

## 项目约定优先

项目自身的 PR 模板与贡献约定（必填小节、字段、顺序）永远赢过本规范；本规范只决定各小节的内容怎么写。

## 写后自检

1. 开头说的是"现在有什么不同"，而不是"我改了什么"？
2. 有没有哪一节、哪一句能从 diff 直接看出来？删掉。
3. 每个 diff 无法证明的论断都写出来了吗？写出来的每个论断都确实是 diff 无法证明的吗？
